1. Dual-Surface System Architecture

The Advanced Dental PRO platform is engineered with a decoupled dual-surface architecture that guarantees lightning-fast static page delivery alongside robust server-side clinical and financial data management.

Client Layer (Next.js 15)

Pre-rendered static HTML/CSS/JS exported via Next.js App Router (output: 'export', trailingSlash: true). Hosted on root domain for sub-second Global CDN delivery.

Server Layer (Laravel 11)

Headless REST API v1 endpoints and AdminLTE 4 Blade management portal hosted under /backend/public/. Manages EMR, appointments, billing, POS, and Yoast SEO.

2. Apache / LiteSpeed Multi-Route `.htaccess`

The root .htaccess file coordinates traffic routing between static Next.js assets, API requests, and Laravel Blade admin routes without request conflicts. 

# Advanced Dental Clinic Production .htaccess Routing
DirectoryIndex index.html index.php

<IfModule mod_rewrite.c>
    RewriteEngine On

    # 1. Force HTTPS in Production
    RewriteCond %{HTTPS} off
    RewriteCond %{HTTP_HOST} !^(localhost|127\.0\.0\.1)(:[0-9]+)?$ [NC]
    RewriteRule ^(.*)$ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]

    # 2. Route API requests directly to Laravel Public Index
    RewriteRule ^api(/.*)?$ backend/public/index.php [L,QSA]

    # 3. Route Admin & Billing requests to Laravel Public Index
    RewriteRule ^(billing|admin)(/.*)?$ backend/public/index.php [L,QSA]

    # 4. Route Storage Symlink
    RewriteRule ^storage/(.*)$ backend/public/storage/$1 [L]

    # 5. Serve static files if they exist on disk
    RewriteCond %{REQUEST_FILENAME} -f
    RewriteRule ^ - [L]

    # 6. Fallback for Next.js Client Portal SPA/Static Pages
    RewriteCond %{REQUEST_FILENAME} !-f
    RewriteCond %{REQUEST_FILENAME} !-d
    RewriteCond %{REQUEST_URI} !^.*(api|admin|billing|backend|storage)
    RewriteRule ^(.*)$ index.html [L]
</IfModule>

4. REST API v1 Endpoints & Payloads

All API endpoints return standard JSON responses with HTTP status codes and strict rate limiting (60 req/min for general endpoints, 10 req/min for appointment booking).

5. MySQL Database Schema & Migrations

The backend relies on 16 relational MySQL tables structured under InnoDB with foreign key constraints, UTF8mb4 character sets, and ACID compliance.

Table Name Engine / Charset Key Columns Description
clinics InnoDB / utf8mb4 id, name, slug, address, city, phone, email, is_active Multi-branch clinic locations and facility metadata.
users InnoDB / utf8mb4 id, name, email, password, role, clinic_id Staff users across 6 granular roles (super_admin, doctor, etc.).
doctor_profiles InnoDB / utf8mb4 id, user_id, clinic_id, specialty, years_experience, rating Clinician credentials, bios, avatars, and consultation fees.
appointments InnoDB / utf8mb4 id, booking_reference, clinic_id, doctor_profile_id, patient_name, appointment_date, appointment_time, status Patient appointment bookings and calendar schedule slots.
dental_charts InnoDB / utf8mb4 id, patient_id, tooth_number, surface, condition, notes Interactive Odontogram EMR surface condition mapping.
theme_settings InnoDB / utf8mb4 id, key, value, group Dynamic visual branding tokens (colors, typography, WhatsApp number).
seo_metadata InnoDB / utf8mb4 id, entity_slug, meta_title, meta_description, og_image, schema_json Yoast-style enterprise SEO metadata and JSON-LD structured data.

6. Hostinger PKZIP Distribution Packaging

To prevent Hostinger/cPanel Linux extraction errors caused by POSIX tarball extensions, the project includes an automated Python packaging script (deployment/package_pkzip.py) that builds standards-compliant RFC 1951 Deflate PKZIP archives. 

# Running local PKZIP compilation utility
python deployment/package_pkzip.py
